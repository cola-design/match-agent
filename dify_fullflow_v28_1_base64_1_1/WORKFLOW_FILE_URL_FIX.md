# V28.2：在流程内补全文件地址

导入 `cabinet_project_v28_2_workflow_files.yml`。继续使用已安装的 Base64 1.1.0 和 PDF-to-Images 1.0.1，无需重新下载插件。

本次针对 `Invalid file URL '/files/...'` 修复 PDF 文件输入、PNG 图片读取和 XLSX 确认表回传。流程将相对文件路径转换为完整地址，保留原始签名和查询参数，并携带完整的 Dify 文件元数据，以兼容 1.8 的运行及调试变量存储。

流程新增环境变量 `DIFY_FILES_BASE_URL`：

```text
http://api:5001
```

默认值是标准 Dify Docker Compose 中的内部 API 地址，用于插件读取 Dify 自己的文件。标准部署可先保留该值。若服务名称或网络不同，在**流程环境变量**中改成插件容器能访问的 Dify 根地址；不包含 `/files`，不填写产品查询服务地址。该方法不要求设置服务器的 `FILES_URL` 或修改服务器 `.env`，但文件服务仍需网络可达。

原有 `MONGODB_API_BASE_URL` 和 `MONGODB_API_KEY` 继续用于产品选型查询，与新增文件地址变量分开。

页面只保留六项操作：

1. 开始选型
2. 提交问题清单
3. 提交选型确认
4. 提交报价表
5. 查看项目
6. 生成排产资料

已移除“继续处理”“修订资料”“保存项目资料”的页面入口和归档输出分支。查看项目在待确认阶段可重新下载当前确认表；产品接口暂时失败后，可修正配置并点击“开始选型”重试。内部阶段和版本校验保留，以支持上述操作。采购报价确认后生成的排产表格仍需工艺复核；DWG 后续补充。

## 验证范围

在真实本地 Dify 1.8 中将服务器的 `FILES_URL`、`INTERNAL_FILES_URL` 同时设为空，保留作者 Base64 1.1.0 和 PDF-to-Images 工具，完成合成 PDF 转图、局部图片处理、确认表生成、三类 XLSX 回传、提前排产拦截、产品选型和已确认报价及排产表格下载。正式 YML 与受控测试变体的编辑页均打开正常。测试还检查了签名参数保留、多页序号选择、已有绝对链接保留和无效根地址拒绝。

视觉模型和产品查询 API 使用受控测试服务；未访问公司内网、未验证真实千问识别准确率。默认内部地址需要符合实际部署的网络和服务名称。

本修复是现有 V28.1 的流程适配。源码 `patch_file_urls.py` 放在 `dify_fullflow_v28_1_base64_1_1` 中，依赖同目录已有的 `graph.py` 和原 YML；运行后生成新的 V28.2 YML。
