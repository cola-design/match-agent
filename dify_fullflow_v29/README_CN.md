# 成套柜项目助手 V29

直接导入 `cabinet_project_v29.yml`。保留你们已经安装的 Base64 1.1.0、PDF-to-Images 1.0.1，以及已经配置的 qwen3-vl-plus。YML 的安装依赖列表为空，不再按固定插件指纹提示重复下载；插件需要已在当前工作区安装。

页面只保留：开始选型、提交问题清单、提交选型确认、提交报价表、查看项目、生成排产资料。采购报价表确认后才允许生成排产表格，DWG 后续补充。

## 本次修正

- 整页概览只提供图纸范围和非器件标注。即使模型违反提示词列出器件，程序也将其单列保留，不重复加入产品清单；概览回路号也不直接作为器件归属依据。
- 局部识别只收到当前图像的任务信息，不再收到全页辅助文字或整页坐标，减少照搬其他区域标注与坐标系混淆。原生全文仍留在最终完整性核对中。
- 使用像素检测有效图面，去掉大片纯白页边，再生成横向、纵向重叠视图。全部裁切保留原像素和颜色，局部位置按程序计算的实际裁切范围映射回整页。无法可靠检测的 PNG 类型保留整页范围，不猜测边界。
- 像素确认的纯白局部跳过模型，记为已覆盖空白；无法看清的非空白区域仍记为未完成，不冒充空白通过。
- 同位置、跨视图且同型号的相别前缀差异可以合并；同型号不同位置继续保留不同实例。同一位置的类别冲突保留为待确认，不按首个结果自动选定。
- 缺少坐标或落在概览子图外的器件读法保存在 `quarantined_observations`，不当成已定位的独立采购器件。这些内容显示在确认表的“识图待定位”页，仍须人工核对漏项。
- 参数关联同时检查可见连线、位置和器件类别。存在冲突时保留原文和问题，不将参数强行挂到邻近器件。
- 重复文档标注按原文合并展示，并保留来源证据；长问题列表按页分表。源确认表的内部组装数据不再误用跨节点字符串预算，最终文件输出仍受原传输限制约束。

100项上限未简单提高，也未宣称新的候选数等于真实器件数量。人工仍需确认器件、柜号、单柜数量、供货范围、厂家和完整性。

## 文件地址与产品 API

`DIFY_FILES_BASE_URL` 沿用流程内地址补全，默认 `http://api:5001`，用于插件读取 Dify 自身文件。该默认值适用于标准 Docker 服务名称和端口；其他部署需改成插件能够访问的 Dify 根地址。无需为了此修复重装插件或设置服务器 `FILES_URL`。

`MONGODB_API_BASE_URL` 填现有产品查询 API 的 HTTP 根地址；数据库连接字符串仍配置在 API 服务端。`MONGODB_API_KEY` 填这套 API 的密钥。识图和问题清单阶段不访问产品库。

## 验证范围

本次运行了9项识图规则测试；对用户原 PDF 的6个新裁切区域逐像素核对，确认保留原像素；对提供的旧输出离线回放，验证概览、无位置和子图外记录单列保留，没有直接丢弃观测来绕过上限。旧模型已经报错的坐标不能通过回放变成正确坐标，回放结果不是识图准确率验收。

本地真实 Dify 1.8 中服务器文件地址配置保持为空，验证现有插件、图片处理、确认表生成、三类 XLSX 回传、提前排产拦截和报价及排产表格下载；空白分支也实际运行过。正式应用和测试变体编辑页打开正常。

本地视觉模型和产品 API 为受控测试服务，没有调用公司真实千问或数据库。**实际识图效果仍需在公司 Dify 上用同一 PDF 再运行验证。** 本地测试通过不等于客户图纸已准确识别。

## 开发复核

`python -m unittest test_v29 -v` 运行通用规则测试；`python build_v29.py` 在仓库现有 V28.2 基础流程上生成新版。可用 `V29_BASE_YML` 指定基础 YML 路径。最终使用者只需导入 YML，不需要部署这些源码。
